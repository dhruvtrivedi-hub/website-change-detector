01

High-level design

One scheduled fetch can serve every user watching the same public URL.

Purpose

Users create watches for public pages, choose an interval and optional CSS regions, and receive alerts when meaningful content changes. Noise filtering, keyword rules, and sensitivity settings reduce unhelpful notifications.

Runtime shape

A single Node.js Express service serves the web UI and JSON API. A scheduler adds due pages to a SQLite job queue; workers fetch each distinct URL once and fan the result out to its watchers.

Browser UILanding, sign-in, dashboard, watch settings

Check lifecycle

  • Scheduler selects due pages and enqueues work.
  • Queue claims jobs with a bounded worker count and lock timeout.
  • Axios fetches public HTML; Cheerio extracts text without a browser.
  • Text is normalized, compared with the last snapshot, and noise filters run.
  • Changed versions persist and deduplicated alerts are delivered.

Deployment boundary

The service requires Node.js 22.13+ for built-in SQLite. HTTP-only scraping avoids Chromium binaries. Render must provide a writable data path for its SQLite database and a stable SECRET value for session and link signing.

02

Service architecture

Bounded work, explicit trust boundaries, and clear failure states.

Web and API layer

src/server.js serves static frontend assets and Express routes. Authenticated routes use the application’s persistent database-backed session cookie. OAuth callbacks establish the same session type.

Scraper and safety

src/scraper.js uses Axios and Cheerio. src/util/ssrf.js checks public addresses and each redirect destination to prevent requests to local or private network hosts.

Queue and scheduling

src/worker.js schedules due page checks and processes leased jobs. Per-host gates limit concurrent requests and enforce a gap between requests to the same host.

Diffs and notifications

Text comparison and noise filtering decide whether a snapshot is meaningful. Alert rows use unique deduplication keys; email, Telegram, Discord, and optional summaries are sent through separate helpers.

03

Low-level design

Small modules with explicit inputs, persisted outcomes, and bounded retries.

Module responsibilities

  • src/server.js — routes, input validation, sessions and account flows.
  • src/queue.js — enqueue, claim, retry, and complete jobs.
  • src/worker.js — fetch, compare, snapshot, and alert orchestration.
  • src/scraper.js — safe HTTP redirects, response classification, and HTML extraction.
  • src/noise.js / src/diff.js — normalization, significance, and comparison output.
  • src/alerts.js — delivery retries and duplicate prevention.

Request and check limits

  • Public URL validation blocks private and loopback destinations.
  • Page response size and request time are bounded.
  • Redirect count, per-host concurrency, and request spacing are bounded.
  • Failed jobs have a retry ceiling; 401/403/429 and challenge pages are classified as blocked.
  • Sign-up passwords have length and composition requirements before hashing.

05

Errors and reliability

Transport failures are recorded as failures, never as content changes.

Failure classification

Timeouts and connection errors are retryable within the job attempt limit. HTTP 4xx, 5xx, rate limits, access blocks, and anti-bot challenges get explicit outcomes. Blocked or failed fetches do not create content snapshots.

Change integrity

Content hashes prevent duplicate versions. Dedupe keys prevent duplicate alerts. Noisy pages can pause alerts until the user adjusts watched regions or sensitivity.

HTTP-only mode reads the initial server response and does not execute client-side JavaScript. Screenshot capture, screenshot diffs, and server-side visual picking are unavailable in this deployment mode.
06

Authentication and sessions

Google and password sign-in converge on the same persistent app session.

Email and password

New passwords require eight or more characters with uppercase, lowercase, numeric, and special characters. Passwords use bcrypt-compatible hashes. Older scrypt hashes are verified and upgraded after a successful login.

Google OAuth 2.0

Passport’s Google strategy handles authorization and callback exchange. A short-lived SameSite state cookie protects the callback. Only verified Google email addresses are linked or registered; provider access tokens are not persisted.

Application session

On either successful sign-in, the app creates a random opaque token, stores only its SHA-256 hash in SQLite, and sends the token in an HttpOnly, SameSite cookie. Sessions persist until sign-out or deletion.

Configuration

Set GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, and optionally GOOGLE_CALLBACK_URL. Register the exact callback URL in Google Cloud OAuth settings. Without credentials, password sign-in remains available.
